# 引导式套牌构筑 Pipeline v1.1

修订日期：2026-10-25。流程规范版本为 1.1；现有阶段 ID 和存储中的 `pipeline_version: 1` 保持兼容，无需迁移旧工程。

目标：玩家在 Agent 引导下，从打法或英雄出发，确认获胜计划，按功能模块完成选牌，最终得到经过验证的套牌工程和 `riftatlas.txt`。

## 对话与工具约定

- 一次只询问一个影响当前选择的关键问题；已经明确的信息直接记录，不重复问。
- 每轮简要显示当前阶段、当前模块（如有）、本次待决定事项和下一步。
- 玩家确认关键方向、模块任务和选牌结果后再推进。一次确认可以覆盖玩家认可的一组卡和数量，不需要逐张重复确认。
- 每轮最多展示 3～5 个单卡候选或 2～3 个机制方案，不强凑数量；比较内容见下文选牌循环。
- 卡牌数据、CLI 前置检查与最终交付遵循本地 skill。通用需求访谈无需等待选定英雄。
- 维护选中、锁定、拒绝和待决记录。锁定说明卡号、区域、数量是否也被锁定；拒绝说明针对单卡、方案还是数量及原因。
- 根据玩家反馈逐步构筑，未获确认的候选不能自动填入草稿。分析、检索、计数、记录和验证可由工具执行。

## 三个入口

### 打法优先：`style_first`

从偏好速度、主动性、单位或法术、复杂度、风险与稳定性中，只补问仍然影响推荐的信息。归纳主要风格及可选的次要风格，推荐不超过三个英雄/Legend 方向，说明效果依据、适配理由和取舍。玩家选择英雄后确认具体 Champion。

### 英雄优先：`hero_first`

先将角色名对应到精确 Legend 选项，分析其效果、领域和可用卡池，再推荐适合的打法。区分自然适配的方向与需要额外条件的实验方向；没有依据时不编造三个方案。选择方向后比较 Champion。英雄与打法冲突时，确认玩家更重视哪一个。

### 尚未确定：`undecided`

最多用三个体验问题建立初步偏好，接入打法优先分支。保留入口记录，在需求数据中注明转入方向。

## 阶段与完成条件

| 阶段 ID | 交付与推进依据 |
| --- | --- |
| `entry` | 创建工程，记录玩家表达或确认的入口 |
| `requirements` | 记录打法体验、英雄偏好、复杂度、必选/禁选和收藏限制；未知项明确标记 |
| `identity` | 确认精确 Legend、Champion 和主要风格 |
| `brief_confirmation` | 玩家接受包含风格、胜利机制、运营方向、核心卡意向与约束的简报；核心卡数量可待定 |
| `core_plan` | 确认主要机制、必要支撑、收益路径和弱点，初步检查资源可行性 |
| `deck_skeleton` | 确认从计划推导的模块及卡位预算，记录依赖和数量依据 |
| `card_selection` | 主牌齐备，模块已确认或明确接受缺口，无未决核心卡位 |
| `resources` | 确认战场、符文和备牌及其资源匹配；备牌写明针对问题与换入换出方向，也可不使用 |
| `review` | 审查曲线、功能、依赖、资源、玩家约束与规则；解决阻塞，披露取舍 |
| `final_confirmation` | 玩家批准即将保存的确切草稿；修改后需重新确认 |
| `completed` | 正式验证通过，首个版本和 `riftatlas.txt` 已生成 |

向前逐阶段推进，可以回到之前阶段。已在需求中明确的信息可以直接用于完成相应阶段，仍需保留记录。阶段内容由 Agent 与玩家完成确认；CLI 目前只检查阶段顺序和最终合法性，不验证语义完成条件。

资源从核心计划阶段持续参与判断，`resources` 负责集中定稿。

## 从获胜计划推导功能模块

使用 [TCG 构筑研究](references/tcg-deckbuilding-principles.md) 作为方法参考。以下功能可用于分析，不是每套牌必填的七个模块：

| 功能 | 核心问题 |
| --- | --- |
| 威胁与得分 | 哪些牌直接推进胜利？ |
| 机制支撑 | 如何提供目标、触发和前置条件？ |
| 机制收益 | 如何把条件转成优势和获胜压力？ |
| 稳定性与续航 | 如何找到所需牌并持续行动？ |
| 干扰与突破 | 必须处理对手哪些行动或障碍？ |
| 保护与恢复 | 如何保住投入或在受挫后重建？ |
| 资源与调度 | 如何支付行动并把资源用于需要的位置？ |

模块按本套牌的任务命名，例如“早期抢场”“防守续航”“核心触发”“战斗突破”。一模块可以涉及多种功能；不需要的模块可以省略。费用、使用阶段、关键程度和针对性单独记录。“灵活卡位”是可调整预算，填入的牌仍要说明任务。

每个模块应记录：

- 稳定模块 ID、名称、任务，以及如何服务获胜计划。
- 功能标签、依赖条件、优先级和预期使用时机。
- 卡位目标及依据，哪些数量是待测试假设。
- 对已选牌的引用、成立条件和选择理由；实体数量以 `draft_deck` 为准。
- 当前状态：`planned`、`in_progress`、`confirmed` 或 `needs_review`。
- 未解决缺口和玩家确认摘要。

选牌顺序由依赖决定：优先解决会决定其余选牌的机制和资源约束，再补影响计划执行的缺口。快攻可优先建立有效压力，控制可先论证后期获胜计划与所需资源，再配前期防守；没有统一的“低费到高费”填牌顺序。

实体数量由唯一的 `draft_deck` 计算，每个副本只计一次；模块通过卡牌引用描述作用，不再保存另一套独立总数。同一牌可覆盖多个功能，但条件收益必须标注，互斥用法不能同时兑现。不能把几张“赢下战斗才补牌”的牌全部当作稳定补牌，也不能直接相加各模块数量得到主牌总数。

## 每轮按模块选牌

1. 指出当前模块缺口及其与获胜计划的关系；方向有分歧时先让玩家选择任务。
2. 从本地合法卡池比较候选的完整 `effect_effective`、费用/身材、独立价值、协同条件、资源要求及落后时表现，给出建议数量。检索评分只作发现提示。
3. 玩家接受单卡或组合、确认数量、比较、锁定、拒绝、换一批或返回。
4. 更新草稿、模块引用、理由和待决问题，检查张数、曲线及功能覆盖，通过 `build-update` 保存。
5. 继续补缺口、确认模块完成，或修正受影响模块。

如果一个选择改变了另一模块的依赖，将后者标为 `needs_review`，保留旧选择和理由。玩家明确接受取舍前，不静默将其改为完成，也不替换锁定牌。

## 暂停、回退与恢复

每次暂停或结束对话前记录当前阶段、模块、已确认决定、最新草稿、未决问题和下一动作。玩家下次说“继续”时先执行 `build-status`，复述这些信息后承接下一项选择。

回退保留已有草稿供比较；身份、核心机制或约束改变时，按上文依赖规则重审。`build-history/` 可读取旧快照，尚无一键恢复命令。

## 持久化约定与实现边界

现有 `build-session.json` 的 `current_stage`、`entry_mode`、`stage_history`、`state.brief`、`identity`、`core_plan`、`skeleton`、`draft_deck`、`locked_cards`、`rejected_cards`、`pending_questions` 继续使用。

模块信息按以下约定存入可扩展的 `state`，下一动作统一记在 `resume.next_action`。待重审状态以模块的 `status` 为准，避免另存一份列表。

```json
{
  "active_module_id": "early-pressure",
  "modules": [
    {
      "id": "early-pressure",
      "name": "早期抢场",
      "task": "在计划需要的时点形成有效压力",
      "functions": ["threat_scoring", "enabler"],
      "dependencies": [],
      "target": {"min": null, "max": null, "basis": "待结合计划确认"},
      "card_refs": [],
      "status": "in_progress",
      "open_issues": ["选择展开方案"],
      "confirmation": null
    }
  ],
  "resume": {
    "next_action": "比较早期展开候选"
  }
}
```

`build-update --state` 输入对象只合并到 `state` 的顶层：传入 `brief`、`modules` 或任何嵌套对象/数组会替换该完整字段，不会深度合并。先读取现有状态，保留该字段已有内容再提交更新。每次成功更新前，CLI 将旧会话保存到 `build-history/`。

`modules[].card_refs` 使用卡号、区域及作用说明引用草稿中的牌。

目前 CLI 可保存扩展字段，但没有模块专用命令、默认初始化、字段校验、统计或依赖失效计算。`finalize-build` 检查所在阶段和合法性，不检查玩家确认凭据或模块完成情况。这些属于 Agent 的流程责任。

命令用法与工程文件定义统一维护在 [套牌工程说明](deck-projects.md)。
